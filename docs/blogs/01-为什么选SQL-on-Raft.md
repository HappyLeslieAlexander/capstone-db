# 为什么选 "SQL on Raft"：设计决策与 trade-off

> 草稿。只写草稿，不发布。

## 问题

要在 3 台机器上做一个能扛 `kill -9` 的 SQL 数据库，可选架构很多：

1. **单机数据库 + 主从复制** (如 MySQL 主从)：主挂了要手动切，有脑裂风险。
2. **分布式 KV + SQL 层** (如 TiDB 思路)：要自己做分片、分布式事务，复杂度爆炸。
3. **SQL on Raft**：3 个节点，每个节点都是"完整数据库"，写操作经 Raft
   复制，多数派确认后提交。

我选了 3。原因很实际：**这是 Capstone，不是生产项目**。目标是把
"SQL 解析执行"和"Raft 复制"这两件事都做对、都讲清楚，而不是堆功能。

## 核心 trade-off

### 复制 SQL 语句 vs 复制 KV 效果

研究员备忘录建议复制 KV 效果 (operation-based)，理由是：
语句复制要求所有副本**确定性重放** —— 如果 SQL 里有 `NOW()`、`RAND()`，
不同副本算出不同结果，数据就分叉了。

我实测后**保留了语句复制**，理由：

- 我的 SQL 子集是**完全确定性**的：没有 `NOW()`、没有 `RAND()`、没有 UDF。
  plan dict 是 `(SQL 文本 + catalog)` 的纯函数。给定相同的日志前缀，
  所有节点算出相同结果 —— 这是数学，不是运气。
- Raft 日志**人类可读**：打开 `/debug`，看到的是一条条 SQL plan，
  不是一堆 KV 二进制。教学和演示时，能指着日志说"看，这条 INSERT
  正在被复制"。
- 分布式测试是证据：kill -9 leader、网络分区、节点重启，三节点行集
  逐行一致，55 行零丢失。

诚实标注：如果将来加 `NOW()`，必须二选一：切到效果复制，或在解析层
直接拒绝非确定函数。没有中间路线。

### 读走 leader，不做 quorum 读

备忘录建议"leaseholder 读"：leader 直接读本地已提交数据，不做 quorum。
我照做了。Follower 的 SELECT 转发给 leader，leader 读自己的已提交状态。

为什么不做更强的 linearizable read (如 Raft 的 ReadIndex)？
因为**单一致性级别先把正确性做对**。我的读语义很明确：
"你读到的是 leader 在某个时刻已提交的数据"。Follower 转发失败时降级为
本地读，但返回里明确标注 `stale_read_possible: true` —— 调用方知道自己在
读什么，而不是被"假装强一致"骗了。

### 全表扫描，而不是二级索引

B+ 树只建在主键上。`WHERE age > 20` 这种非主键条件就是全表扫描。

这不是懒，是**诚实**：二级索引的维护 (写放大、一致性) 是另一个大题目。
Capstone 的增量是"SQL 层"，不是"索引层"。README 里写清楚性能含义，
让用的人知道 1000 行可以、100 万行不行 —— 比假装支持然后慢到不可用要好。

### 单语句原子，不做分布式事务

每条写语句 = 一条 Raft 日志 = 一次本地事务。不支持 `BEGIN/COMMIT`、
不支持跨语句事务。备忘录也认可"单语句原子 + 单分片 BEGIN/COMMIT"是个
合理的止损点，我连 BEGIN 都没做 —— 因为 Raft 日志本身是全局有序的，
多语句事务的隔离语义要另起一套机制，超出本次范围。

## 没选的路

- **分片 (sharding)**：3 节点全是完整副本，没有分片。分片要解决数据分布、
  跨分片查询，是下一个 Capstone 的题目。
- **MVCC 跨节点**：存储引擎有 MVCC，但只用于单机事务。Raft 层面不做
  多版本，读到的就是已提交最新版。

## 一句话总结

SQL on Raft = **用 Raft 解决"写去哪"，用单机引擎解决"怎么写"**。
两层各做一件事，都做对了，合起来就是一个能扛 kill -9 的数据库。
