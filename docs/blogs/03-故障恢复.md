# 故障恢复是怎么保证"不丢一条"的：Raft 提交 + WAL 双保险是怎么咬合的

> 草稿。只写草稿，不发布。

## 两层保险，各保什么

- **Raft**：保证"已提交的写不丢"。只要多数派确认了，即使 leader 被
  `kill -9`，新 leader 的日志里也有这条。
- **WAL** (存储引擎的)：保证"已提交的事务不丢"。即使进程被 `kill -9`，
  重启后重放 WAL，B+ 树回到崩溃前的已提交状态。

问题：这两层是怎么**咬合**的？中间有个缝：Raft 说"已提交"，WAL 说
"已落盘"，如果节点在"Raft 已提交但 WAL 还没写完"时被杀，重启后会不会
漏掉这条？会不会重放两次？

## 咬合点：applied 游标

每个节点的本地存储里，除了用户数据，还有一个特殊的 KV：

```
("\x00meta", "applied") -> {"index": 42}
```

意思是"Raft 日志里前 42 条，我已经在本地执行完了"。

关键设计：**执行第 43 条语句的效果，和把游标从 42 改成 43，
在同一个 MiniDB 事务里提交**。代码在 `store.apply_committed`：

```python
txn = self.db.begin("RC")
result = apply_plan(self, txn, plan)   # 语句效果
txn.put(APPLIED_KEY, {"index": index})  # 游标
txn.commit()  # 原子提交，要么都有，要么都没有
```

MiniDB 的事务提交是 WAL 先行 (write-ahead)：WAL 落盘了才返回。
所以：

- 如果 `kill -9` 在 `commit()` 返回前：WAL 里没有这个事务，
  重启后游标还是 42，Raft 重放第 43 条时重新执行 —— **不丢**。
- 如果 `kill -9` 在 `commit()` 返回后：WAL 里有，游标是 43，
  重启后从 44 开始重放 —— **不重**。

"不丢 + 不重"就靠这个原子性。这是整个系统正确性的基石。

## 重启后的三步

节点重启时 (`DBNode._load`)：

1. 打开本地存储，读 `applied` 游标 (比如 42)。
2. 打开 Raft 日志，发现 `commit_index` 是 50。
3. 重放第 43～50 条 (只重放已提交的)，每条走上面的 `apply_committed`。

如果 `applied > commit_index` 呢？(存储事务提交了，但 Raft 的 `_save`
还没落盘就 crash) —— 取较大者，直接设 `last_applied = max(...)`，
不重放。游标是 ground truth。

## 实测中抓到的三个 bug

### Bug 1：页号复用

`allocate_page()` 用 `num_pages()` (文件大小) 分配新页号。但它只做
buffered write 不 sync，`kill -9` 可能丢掉这次文件扩展。重启后文件变小，
新页号复用了一个已存在的页 → B+ 树成环 → 持锁线程永久卡死。

修复：内存里维护单调递增的高水位 `_next_pid`，启动时用
`max(文件页数, WAL 最大页号 + 1)` 初始化。页号永不复用。

### Bug 2：Redo 顺序

WAL 重放时，我最初按 LSN 顺序混排物理 (PAGE_WRITE) 和逻辑
(KV_UPDATE/COMMIT) 操作。但早期的 COMMIT (LSN 66474) 会在后期的
PAGE_WRITE (LSN 9048286，新 root 页) 还没重放时，用 final root 去查
一个还是全零的新页 → "key missing" 误报。1000 行 kill -9 必现。

修复：Redo 分两遍，先物理后逻辑。第一遍把所有页面带到最终状态，
第二遍做逻辑重放时树结构已稳定。

### Bug 3：先推进游标再执行

Raft 的 `_apply_new` 原来是先 `last_applied += 1` 再 `_apply_entry`。
如果 apply 抛异常，这条已提交的日志被永久跳过 —— 重启后
`last_applied = max(commit, applied)` 直接越过它。

修复：apply 成功后才推进。失败就停住，重启后从游标重放。

## 演示

`demo/fault_recovery.sh`：写 1000 行 → `kill -9` 两台 (含 leader) →
重启 → 三节点 1000 行零丢失。transcript 在 `demo/transcript.txt`。

这 1000 行每一行都经过了上面的双保险：Raft 多数派确认 + 本地 WAL 原子
提交。杀掉两台，剩下一台没有多数派 (不能写，这是 Raft 的正确行为)；
重启后，落后的节点从 leader 追日志，用 `applied` 游标保证不丢不重。
